1. Current testing state (before this work)

What existed

  • 88 Go tests: 52 unit and 36 integration. The strongest were 29 service-level dental money tests (undo or correct a visit, fee guards, parallel collect bills once, day close).
  • One RLS test, covering the users table only.
  • Frontend: no test runner. One ad-hoc script that nothing ran.
  • "E2E": shell scripts run against production as the database superuser, with a committed test password (audit TST-4).

What was wrong with it

  • CI ran 4 of the 36 integration tests. Its -run Integration filter skipped all 29 dental money tests.
  • CI never ran on the deployed branch, only on master and pull requests, and master is 191 commits behind.
  • CI's module-boundary lint was already red. It rejected the dental test for importing billing.
  • The one RLS test failed when run (see RLS-GUC-1).
  • No HTTP-level tests at all: permissions, routing and clinic isolation through the real API were never exercised. Frontend lint was not in CI.

2. Testing architecture

Unit Go: pure rules (ids, phone, SMS segments, Verify.ET decision, pregnancy, seal) 52 + 36 tests Vitest: visit words & money, visit focus, Ethiopian calendar, dashboard format & links, patient edit dialog (component) ↓ Integration Go service + real Postgres: dental money rules D1–D13, notifications, provisioning, RLS 36 tests ↓ API regression backend/tests/regression — the REAL api binary, connected as the RLS role clinic_app 106 tests (exactly like production), driven over HTTP. Two clinics, a user in every role. ↓ End-to-end frontend/e2e — Playwright in a real browser, real API, real test clinic 5 journeys ↓ regress.sh one command, one readable summary, exit code 0 only when nothing broke ↓ CI .github/workflows/ci.yml — same suites on every push; red means do not deploy

Why the API layer is the backbone

Most behaviour a clinic depends on is visible at the HTTP boundary: who may do what, whether clinic A can reach clinic B, what a balance says after a payment, which state changes are refused. A test there exercises routing, middleware, permission checks, validation, SQL and row-level security together. Because it only uses the public API, it survives refactoring.

Tests set up their data through the API too. So if "create patient" breaks, every test that needs a patient fails loudly; nothing hides it by inserting rows directly.

Why each other layer exists

  • Service integration tests cover rules with many branches cheaply. The dental money rules have about 30 cases.
  • Unit tests cover deterministic logic where the cases are cheap: calendar conversion, visit wording, focus rules.
  • E2E tests are deliberately few. They are slow and brittle, so they cover only the journeys a clinic lives on.
  • The database superuser is used only to inspect what was really stored, or to set up what the API cannot, such as back-dating a payment to 00:30.

Safety guarantees

  • The test database guard fails the run unless the host is local and the database name contains "test" or "regress". A misconfigured shell cannot reach a clinic's data.
  • The API under test starts with a clean environment. Exported SMS, storage, AI, Verify.ET or DHIS2 keys never reach it. SMS goes to the log gateway, files to a no-op store, and nothing external is contacted.
  • Each money test gets a private clinic, so totals are exact and tests never share state. Parallel runs are serialised at setup by a database advisory lock.

Product code changed

None. Only test files, test tooling and CI changed. Two tooling fixes:

  • Module-boundary lint: it now skips test files and the test toolkit. Tests arrange real cross-module scenarios; the rule protects product code, and it was already failing CI on the existing dental test.
  • RLS test: its failure is now reported as a known bug, checked precisely, so any other error or any visible row still fails it hard.

8. CI/CD

push / pull request (master, main, refine/**) ├─ backend-static build · vet · module boundaries · unit · sqlc (informational) ├─ regression Postgres service → every Go test (unit + integration + API) → summary + JUnit ├─ frontend eslint · tsc · vitest · build ├─ e2e (after regression + frontend) Playwright, bundled Chromium └─ secrets gitleaks ALL GREEN ─────────────▶ deploy allowed ANY RED ─▶ deploy blocked, read the job summary

To make the gate real

  1. Push this branch once and watch the first CI run. This environment could not reach GitHub to run it, so the workflow is written and its suites run locally, but CI itself has not run yet.
  2. In GitHub → Settings → Branches, protect the deploy branch and require the regression, frontend and e2e checks.
  3. Add a check to deploy.sh that the commit being deployed has a green CI status (GitHub API with a read-only token), and refuse otherwise. Until then the rule is a human one: no deploy from a red or unknown commit.
  4. Run regress.sh locally before pushing. It is the same suite, so CI should never be the first to say no.

9. Developer workflow

make a change ↓ scripts/test/regress.sh --quick (seconds) ↓ scripts/test/regress.sh (minutes) ↓ red? read the failure: test name, file:line, expected vs actual ↓ fix → run again → all pass ↓ commit → push → CI green ↓ deploy

Everyday commands

  • Everything: scripts/test/regress.sh --e2e
  • No database to hand: scripts/test/regress.sh --db-up (Docker)
  • Only dental: make -C backend test-dental
  • Only payments: make -C backend test-payments
  • Only permissions: make -C backend test-auth
  • One test: go test ./tests/regression/ -run REG_PAY_005 -v
  • Frontend while coding: npm run test:watch
  • Every open bug as red: REGRESSION_STRICT=1 scripts/test/regress.sh

Every production bug: reproduce it, write a failing test, fix it, keep the test. If the fix must wait, commit the test with KnownBug("<id>", …) so the bug stays visible.

10. Proof it catches regressions

A suite that passes proves nothing until it is shown to fail. Two realistic mistakes were planted, run, and then reverted (the files were restored to the committed version byte for byte):

Backend: "owed" doubled in Receivables

One SQL expression changed. Three tests failed, each saying exactly what broke:

✗ TestREG_PAY_008_VoidAndWaiveStopTheDebt
    receivables before: owed "1000.00", want 500

Frontend: a payment word changed
