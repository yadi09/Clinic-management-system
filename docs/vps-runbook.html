01Connecting

One key, one account. Run this from your own laptop.

ssh -i ~/.ssh/The-millions themillions@77.68.116.240

The -i matters. Without it SSH offers your default key, the server refuses it, and you get Permission denied (publickey) — which looks exactly like your access has been revoked but means only that the wrong key was offered.

Make it one word instead

Add this to ~/.ssh/config on your laptop, and from then on ssh vps is enough:

Host vps
  HostName 77.68.116.240
  User themillions
  IdentityFile ~/.ssh/The-millions
  IdentitiesOnly yes

That account is in the sudo and docker groups with passwordless sudo, so it is effectively root. Everything below assumes you are logged in as it.

03A site is down — work through this in order

Each step tells you whether the problem is above or below it. Do not skip ahead.

Step 1 — is it just you? 
curl -sS -o /dev/null -w "%{http_code}\n" https://www.the-millions.co.uk/

200 = the site is fine, the problem is your browser or your network. Stop here.
A certificate error = jump to Certificates, that is the most likely cause.
000 or a hang = keep going.

Step 2 — is the server itself alive? 
ssh vps 'uptime'

If this fails too, the machine or the network is down — that is a hosting-provider problem, not something you fix from here.

Step 3 — is it working on the box but not outside? 
ssh vps 'curl -k -s -o /dev/null -w "%{http_code}\n" -H "Host: www.the-millions.co.uk" https://localhost/'

200 here but broken outside means the application is healthy and the problem is between the internet and the box — nearly always the certificate. This is exactly what the September outage looked like.

Step 4 — are the containers up? 
ssh vps 'docker ps --format "{{.Names}} {{.Status}}"'

Something missing or restarting → see Restart & logs.

Step 5 — is the disk full? 
ssh vps 'df -h /'

At 100% everything fails in confusing ways at once. Go to Disk space.

04Certificates

The most likely cause of a total outage on The Millions.

Check the expiry date

echo | openssl s_client -connect www.the-millions.co.uk:443 \
  -servername www.the-millions.co.uk 2>/dev/null | openssl x509 -noout -dates

Read notAfter. Certificates last 90 days. Current one expires 23 December 2026.

Renew it

ssh vps 'cd ~/The-Millions/deploy && ./issue-cert.sh'

Takes about a minute and ends with ✅ Let's Encrypt cert issued. It does nothing if the current certificate still has more than 30 days left, so running it when unsure is safe.

expect The script stops nginx for a few seconds to free port 80. The site is briefly down during renewal — which is why it is better done deliberately than at 3pm on a Tuesday.

limit Let's Encrypt allows 5 certificates per domain per week. Normal use never approaches this; repeatedly re-running the script in one afternoon would.

05Deploying ClinicOS

Code is pushed to GitHub from your laptop, then pulled on the server. One command does the rest:

# on your laptop, first
git push origin refine/clinic-ops

# then deploy
ssh vps '~/clinicos/scripts/deploy/deploy.sh'

It fetches the branch, resets to it, rebuilds, runs migrations, restarts, and checks the app answers before reporting success. It refuses to start if .env or the TLS files are missing, rather than leaving you with a server that builds and then cannot boot.

Ends with ==> Deployed <commit>. Anything else means it stopped deliberately — read the last line, it names the reason.

07Looking at the databases

# ClinicOS
docker exec -it clinicos-postgres-1 psql -U clinic -d clinic

# The Millions
docker exec -it themillions-postgres-1 psql -U themillions -d themillions

Inside psql: \dt lists tables, \q quits. A one-off query without the interactive prompt:

docker exec clinicos-postgres-1 psql -U clinic -d clinic -c "SELECT count(*) FROM patients;"

Take a manual backup before anything risky

docker exec clinicos-postgres-1 pg_dump -U clinic clinic | gzip > ~/clinicos-$(date +%F).sql.gz
docker exec themillions-postgres-1 pg_dump -U themillions themillions | gzip > ~/millions-$(date +%F).sql.gz

important There are no automatic backups. These two commands are currently the only copies that will ever exist, and a file on the same server is not really a backup — copy it to your laptop afterwards with scp.

08Disk space

df -h /

At the last audit: 81% used, 23 GB free. It climbs with every ClinicOS deploy because Docker keeps build caches. When it reaches 100%, PostgreSQL cannot write and both businesses fail at once.

Reclaim space safely

docker builder prune -af

Frees roughly 30 GB in under a minute. Safe: build cache is regenerated automatically on the next deploy and holds nothing unique. Run it whenever df shows 85% or more.

To see where space has gone:

docker system df
sudo du -h --max-depth=1 /var/lib | sort -rh | head

09Never do this

CommandWhat it destroys
docker compose down -v Deletes the database volume. Every patient record, permanently, with no backup to restore from. The -v is the whole difference.
docker system prune -a --volumes Same outcome by a different route — the --volumes takes the databases with it.
git clean -fd in ~/clinicos Removes .env and the TLS certificate and key, which exist only on this server. The site stops and cannot restart until they are reissued.
rsync --delete into infra/ Same files, same outcome.

The pattern worth remembering: anything with -v, --volumes or --delete deserves a pause. Everything else on this page is recoverable; these are not.

11Known quirks, so they do not alarm you

  • nginx is permanently "unhealthy". Broken healthcheck, not a broken server. Ignore it.
  • clinicos-migrate-1 shows Exited (0). Correct — it runs once per deploy and stops.
  • nginx logs a "conflicting server name" warning on every start. Harmless duplicate config block.
  • postgres — Up 2 months after a deploy. Correct and good: deploys rebuild the app and deliberately leave the database alone.
