CRM merge plan

Taking the best of the Vercel prototype into the ClinicOS CRM · 25 September 2026

Yes — ClinicOS is the one to keep, and it is stronger than it looks. The prototype is a better shop window; ClinicOS is a better shop. Its prospect record already carries 24 fields including priority, next action, source and map URL, and it has things the prototype structurally cannot have: real multi-user data, duplicate detection, and a link from a prospect to the clinic workspace it becomes. Port the prototype's interface and its three genuinely new ideas onto that spine. Do not rebuild.

The prototype is what a v0-style tool produces and it is a genuinely good specification. It is not a system: clear the browser and the pipeline is gone, and two reps on two laptops would never see the same board.

02Data model, field by field

The reason this is a port and not a rebuild.

ClinicOS crm_prospects already holds:

clinic_name  contact_name  contact_role  phone  phone_alt  email
address      map_url       note          source partner_lead_id
owner_id     status        priority      next_action  next_action_at
ready_on     outcome_note  tenant_id     created_by   … + timestamps

That covers most of the prototype's lead table already — including contact_role (Owner / Doctor / Manager / Receptionist), source, priority, and map_url for the Google Maps origin.

Genuinely missing, and worth adding

FieldWhy it earns its place
subcityThe prototype filters on 33 named Addis subcities. Today ClinicOS has free-text address, which cannot be filtered, grouped or used for territory. This is the single most Ethiopian-specific idea in the prototype.
rating, reviews_countLeads come from Google Maps, which gives both for free. A 4.8-star clinic with 104 reviews is a different prospect from a 3.8 with 12 — real qualification signal at zero cost.
scoreComputed, not typed. See phase 3.

What ClinicOS has that the prototype cannot

  • tenant_id on a prospect — the link from "clinic we are courting" to "clinic running ClinicOS". That closes the loop from sale to customer, and a localStorage app has nothing to close it to.
  • Duplicate detection (/prospects/duplicates) — four reps sourcing from Google Maps will collect the same clinic twice.
  • Configurable phases per campaign — the prototype hardcodes 11 stages; ClinicOS lets a campaign define its own, which is strictly more flexible.
  • Outcome / reopen lifecycle and an inbound importer from partner_leads.

04The interface — how to port the look without the architecture

Both are React with Tailwind, so this is a re-skin, not a rewrite. The prototype's visual language maps onto components ClinicOS already owns:

PrototypeBuilt in ClinicOS from
Left sidebar with counts and an OVERDUE badgeExisting console nav + the Segmented badge pattern already used on Reception and Chairside
Saved-view tab stripSegmented — the same component as Chairside's lenses
Stage / priority pillsBadge with variants
Dense sortable tableTable + the column pattern from the Staff page
Filter row of selectsSelect
Lead detail drawerExisting ProspectDialog, widened
One deliberate departure. The prototype is a light-on-white admin app; the ClinicOS platform console is dark. Porting the layout wholesale into the dark console will look wrong. Take the structure — sidebar, view tabs, filter row, dense table, pills — and keep the console's own palette. Copying the colours as well is the quickest way to make it look like two products stitched together.

05Implementation plan

Ordered so a rep gets something useful at the end of every phase, not only at the end.

Phase 1 — The list becomes workableno schema change~1 session
  • Dense prospect table: stage and priority pills, contact, rep, last touch, next action
  • Saved-view tabs: All · My Leads · Hot · Overdue · Uncontacted · Demos · Won · Lost
  • Filter row: status · priority · owner · source
  • Sorting and pagination

Why first: it is the screen a rep lives in, it needs no migration, and ListProspects already accepts status, owner and priority. Highest value per hour on the whole list.

Phase 2 — Follow-ups become a real queuenew table~1–2 sessions
crm_tasks(id, prospect_id, title, due_at, done_at, owner_id,
          kind, note, created_by, created_at)
  • Queue with Overdue / Today / Upcoming / Completed
  • Snooze +1 day / +3 days; complete; reassign
  • Keep next_action_at on the prospect as a derived convenience so nothing breaks

Why second: 68 overdue follow-ups in the prototype is the number that shows what this screen is for. One next_action per prospect cannot express a rep's day.

Phase 3 — Lead quality3 columns~1 session
  • Add subcity, rating, reviews_count to prospects
  • Score computed server-side from configurable weights — rating, review count, stage age, touch count, source — so the number is explainable rather than magic
  • Subcity filter and territory grouping

Decision needed: scoring rules fixed in code, or editable in the console? Editable is what the prototype shows and it is more work. My view: start fixed, expose later once you know which weights you actually argue about.

Phase 4 — Analyticsqueries only~1 session
  • Funnel drop-off from crm_phase_events
  • Rep leaderboard: assigned · contacted · demos · activities · won · win rate
  • Source ROI and subcity density (needs phase 3)

No new tables. Every figure already exists in the data; it has simply never been asked for.

Phase 5 — Getting leads in~1 session
  • Excel / CSV import with column mapping, a dry run, and duplicate detection against the existing /prospects/duplicates
  • Reuse the patient CSV importer's patterns — that work is already done and proven
Phase 6 — Polish~1 session
  • Calendar over tasks · activity-channel filters · prospects in the Ctrl-K palette

06What I would not do

  • Do not migrate the prototype's data. 100 fabricated clinics with invented doctors and ratings would pollute a real pipeline that currently holds 7 genuine prospects. Start from the real seven.
  • Do not port all 11 stages as fixed. Seed them as one campaign's phases and expect to cut to five or six once four reps have to keep them honest.
  • Do not rebuild auth or team management. That is the one area where ClinicOS is overwhelmingly ahead and the prototype is a drawing.
  • Do not do this before the backups. Adding tables to a database with no backup increases what there is to lose. That job is still outstanding.

07Decisions I need from you

  1. Stages: keep all 11, or cut to a shorter ladder? I would propose New → Contacted → Interested → Demo → Trial → Negotiation → Won/Lost.
  2. Scoring: fixed weights in code first, or configurable from day one?
  3. Scope: all six phases, or stop after 1–3 and see whether the reps use it?
  4. Where it lives: stay inside the platform console (vendor-side, where it is now), or become its own app at /crm? The prototype's full-screen sidebar layout implies the latter.
Prepared 25 September 2026. The prototype was examined by reading its bundle and driving it in a browser; the ClinicOS CRM by reading its schema, its 23 endpoints and its frontend. No code has been changed — this is a plan, not an implementation.
