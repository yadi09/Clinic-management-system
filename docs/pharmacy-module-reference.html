1 · Dispense queue — Dispense queue (Pharmacy)

A read-only, auto-refreshing worklist of signed (doctor-closed) prescriptions waiting to be dispensed, with four KPI tiles and a table whose actionable rows link into the per-prescription dispense workspace.

route /pharmacy/queuenav: Dispense queue

Permissions & gating

Backend GET /pharmacy/dispense-queue requires permission "pharmacy.read" (routes.go:14,18) AND the "pharmacy" feature flag (routes.go:12, httpx.RequireFlag("pharmacy")). The nav entry is shown to holders of "pharmacy.read" OR "pharmacy.dispense" (nav.ts:35, perm: ["pharmacy.read","pharmacy.dispense"]). Opening a row leads to the detail/dispense page; the dispense actions there (prepare/complete) require "pharmacy.dispense" (routes.go:22-24). NOTE: the frontend route /pharmacy/queue itself is only wrapped by ProtectedRoute + AppShell (router.tsx:55-70) — there is no per-route permission guard component in the router, so gating is enforced server-side and by nav visibility, not by a client route guard.

Small pharmacy

In a single-pharmacist shop the same person watches this screen all day. It polls every 30s (DispenseQueuePage.tsx:19, refetchInterval: 30000), so when a doctor closes an encounter and the Rx appears with status "ready", the pharmacist clicks the row to open the dispense workspace, picks batches, prices it (prepare → sends a pharmacy charge to the cashier), takes payment, and hands over (complete). The "allergy check" flag and the awaiting-payment/dispensed badges let one person track where each Rx is without leaving the page. The four KPIs (To dispense / Dispensed today / Low stock / Near expiry) double as the only at-a-glance status board they need.

Large pharmacy

In a larger pharmacy with several staff and separated duties this is the intake board for the dispensing bench. Multiple "pharmacy.read"/"pharmacy.dispense" staff watch the queue; the cashier (a separate billing role) collects the pre-pay charge that prepare raises, and only then can a dispenser complete the hand-over (CompleteDispense gate on charge status "paid"/"waived", service.go:343-345). The "awaiting payment" badge tells the bench which Rx are stuck at the cashier vs "ready" to be picked. The list is capped at the 100 most recent prescriptions (ListDispenseQueue LIMIT 100, pharmacy.sql:95) ordered undispensed-first then by rx_no DESC, so high-volume sites see newest work first. There is no per-row claim/lock on this list (the double-dispense guard is enforced atomically only at complete via MarkPrescriptionDispensed), so two dispensers could open the same row; the concurrency guard catches the conflict at completion, not on this screen.

Workflow

  1. Page mounts and calls dispenseQueue() → GET /pharmacy/dispense-queue (api.ts:77-79, DispenseQueuePage.tsx:19).
  2. React Query refetches automatically every 30 seconds (refetchInterval: 30000).
  3. Four KPI tiles render from data.kpis: To dispense, Dispensed today, Low stock, Near expiry; each shows an em-dash placeholder when data is undefined (lines 30-33).
  4. The table lists data.items. Each row shows Rx number (R-{rx_no}), patient name + MRN, prescriber, item count, flag badges, and a status badge.
  5. Status badge is derived purely client-side: 'dispensed' (success) if it.dispensed, else 'awaiting payment' (warning) if it.awaiting_payment, else 'ready' (outline) (lines 69-71).
  6. Rows that are NOT yet dispensed are clickable (cursor-pointer hover) and navigate to /pharmacy/dispense/{it.id} on click; dispensed rows are inert (no click handler fires) (lines 52-54).
  7. If there are zero items, an empty state explains that signed prescriptions appear here for dispensing (lines 77-85).
  8. All dispensing actions (batch picking, pricing, hand-over) happen on the linked DispensePage, not on this page — this page is strictly a read-only worklist.

Gaps & observations

Flag is coarse, not a real conflict: the 'allergy check' flag only means the patient has ANY allergy on file (EXISTS allergies, pharmacy.sql:86) — it does NOT mean the prescribed drugs conflict. The actual class-aware conflict check (allergyMatchesDrug) runs only on the detail/prepare path (service.go:175,266,370), so the queue can show 'allergy check' for harmless cases and cannot pre-flag a true conflict.
TS type omission: the DispenseQueueItem interface (frontend/src/features/pharmacy/api.ts:30-40) does not declare a `dispensed` field, yet DispenseQueuePage.tsx reads it.dispensed at lines 52,53,69,70. It works at runtime because the backend serializes json:"dispensed" (ports.go:54), but the type is unsound.
No client-side permission guard on the route: /pharmacy/queue is mounted under only ProtectedRoute+AppShell (router.tsx:55,70) with no per-route RequirePermission wrapper; access control relies on server enforcement and nav-link visibility (nav.ts:35).
UTC day boundary for 'Dispensed today': startOfDayUTC() (service.go:780-783) is used for the dispensed_today KPI (service.go:114), so for an Ethiopia (UTC+3) clinic the 'today' count rolls over at 03:00 local time, not midnight local.
Hard-coded 90-day near-expiry window: nearExpiry := time.Now().AddDate(0,0,90) (service.go:115) and batchStatus's 90-day threshold (service.go:731) are not configurable per clinic.
No filtering/search/pagination on the page: the table is whatever ListDispenseQueue returns, hard-capped at LIMIT 100 (pharmacy.sql:95) ordered by dispensed-first then rx_no DESC. There is no UI to filter by patient, date, status, or to page beyond 100 — unlike other 'windowed' pages mentioned in repo history.
includeDispensed always true: the service passes IncludeDispensed=&true unconditionally (service.go:111,123), so already-dispensed Rx remain in the list (rendered as inert 'dispensed' rows) with no way to hide them from this page.
No loading or error UI: the page does not handle q.isLoading or q.isError (DispenseQueuePage.tsx); during load it shows '—' KPIs and an empty table, and on fetch error it silently shows the empty state ('Nothing to dispense right now', lines 77-85) rather than an error message.
KPI/flag mismatch with the list: KPIs (to_dispense, etc.) are tenant-wide counts (pharmacy.sql:200-211) while the table is capped at 100 rows, so 'To dispense' can exceed the number of undispensed rows visible.
Legacy/unused sale statuses: 'charged' and 'paid' remain in the pharmacy_sales CHECK (00017:17-18) but the current dispense flow only writes 'awaiting_payment' then 'dispensed' (or 'cancelled'); 'charged'/'paid' are dead values for sale_type='dispense'.
No real-time updates beyond 30s polling: changes (a new signed Rx, a cashier collecting payment) only surface on the next 30s refetch (line 19); there is no websocket/event-driven refresh.

2 · Dispense detail (subpage) — DispensePage (Dispense — R-{rx_no})

Per-prescription dispensing workspace where a pharmacist verifies allergies, picks a stock batch (FEFO) and quantity per item, prices the fill and sends it to the cashier, then hands the medication over once the cashier confirms payment.

route /pharmacy/dispense/:rxIdnav: Dispense queue (entry point); the per-Rx screen has no own nav item

Permissions & gating

Backend: GET detail requires pharmacy.read; POST prepare & POST complete require pharmacy.dispense. Whole module gated by the `pharmacy` feature flag (RequireFlag). Frontend route is only auth-gated (ProtectedRoute) with NO per-route permission check — see gaps.

Small pharmacy

In a single-pharmacist shop one person holds pharmacy.read + pharmacy.dispense (and is often also the cashier). They still go through the two-step flow: 'Send to cashier' to bill, then collect the money at the till, then 'Complete dispense'. Because hand-over is hard-gated on the charge being 'paid'/'waived', even a solo operator cannot accidentally give out meds before the sale is recorded. The allergy pills and per-line BLOCKED badge are the safety net a small site lacks a clinical-pharmacist review for. For unstocked drugs, the 'Not in stock — print & buy outside' note plus the Print button lets them hand the patient a paper script.

Large pharmacy

In a multi-staff hospital pharmacy this enforces separation of duties end to end: a dispensing pharmacist (pharmacy.dispense) verifies the allergy banner/red pills, selects the correct lot via the Batch (FEFO) dropdown to rotate stock and avoid near-expiry waste, sets quantity, and clicks 'Send to cashier' — pricing the fill and raising a pending pharmacy charge. The patient pays at a separate cashier station (page shows the amber 'Awaiting payment — ETB X due at the cashier' banner); only after the cashier settles does the green 'Payment collected … Ready to hand over' banner appear and 'Complete dispense' unlock. Completion atomically claims the Rx (dispensed_at guard stops two pharmacists double-dispensing the same script), decrements the exact chosen batches, and writes stock_movements for audit. Catalog/stock are owned by separate roles (pharmacy.manage / pharmacy.stock) on other pages. Out-of-stock/unmatched items are flagged 'Not in stock — print & buy outside' so high-volume sites can route those externally without blocking the rest of the fill.

Workflow

  1. Pharmacist opens the queue (/pharmacy/queue) and clicks a non-dispensed prescription row, navigating to /pharmacy/dispense/:rxId (DispenseQueuePage.tsx:53).
  2. Page calls GET /pharmacy/dispense/:id; backend loads header, patient allergies, prescription items matched to catalog drugs by name, FEFO batches, per-item allergy verdicts, and any existing prepared sale (pre-pay state).
  3. On load, the page initialises each item's selection to the first AVAILABLE batch (qty_on_hand>0, not quarantined, not expired) and qty=1.
  4. Pharmacist reviews the red allergy pills / amber reminder and any per-line '— BLOCKED' markers; if any line has an allergy_conflict the whole fill is blocked.
  5. For each dispensable line, pharmacist picks the batch from the Batch (FEFO) dropdown and sets Qty; unmatched/out-of-stock lines show 'Not in stock — print & buy outside' instead of inputs.
  6. Pharmacist optionally types counselling notes, then clicks 'Send to cashier' (disabled if blocked or no valid lines).
  7. POST /pharmacy/dispense/:id/prepare validates each line (drug exists, allergy guard, batch belongs/not quarantined/not expired, qty>0), computes subtotal=Σ unit_price*qty, raises a pending pharmacy charge, and inserts a pharmacy_sales row status 'awaiting_payment' + sale items — NO stock moves. Toast 'Billed ETB {total} — sent to the cashier'; page refetches into the awaiting-payment view.
  8. Patient pays at the cashier (separate billing module). On refetch/reload the page shows green 'Payment collected … Ready to hand over' once the charge is 'paid' or 'waived'.
  9. Pharmacist clicks 'Complete dispense' (enabled only when charge_settled).
  10. POST /pharmacy/dispense/:id/complete re-checks payment, atomically claims the Rx (dispensed_at), re-runs allergy + batch checks, decrements each chosen batch, writes stock_movements (reason 'dispense'), and flips the sale to status 'dispensed'. Toast 'Dispensed — stock decremented, handed over' and navigate back to /pharmacy/queue.
  11. (Optional) Pharmacist clicks Print at any point to print the screen for the patient (e.g. for buy-outside items).

3 · OTC sale — OTC Sale (Over-the-Counter walk-in sale)

A counter point-of-sale screen for selling stocked drugs to a walk-in with no prescription and no patient record: search the catalog, build a cart, apply a flat discount/tax, pick a payment method, and the backend auto-picks an in-date FEFO batch per line, decrements stock, and records an immediately-'paid' OTC sale.

route /pharmacy/otcnav: OTC sale

Permissions & gating

Action gated by `pharmacy.sell` (backend: routes.go:25 — `g.POST("/otc", httpx.RequirePermission("pharmacy.sell"), h.SellOTC)`). Drug search gated by `pharmacy.read` (routes.go:16 — `g.GET("/drugs/search", read, h.SearchDrugs)`). Whole pharmacy module behind the `pharmacy` feature flag (routes.go:12 — `httpx.RequireFlag("pharmacy")`). Frontend nav link visibility gated by `perm: ["pharmacy.sell"]` (nav.ts:36). GAP: the React route itself (router.tsx:74) sits only inside `<ProtectedRoute />`, which checks authentication only (ProtectedRoute.tsx — no permission/role/flag check); any authenticated user can open /pharmacy/otc by URL and run a drug search (needs only pharmacy.read), but the Take payment POST is rejected by the backend without pharmacy.sell.

Small pharmacy

In a single-pharmacist shop this is the everyday register: a walk-in asks for paracetamol or a bandage, the pharmacist types the name, taps the result to add it, bumps the quantity, optionally types a discount, picks Cash, and hits Take payment. Stock is decremented automatically against the earliest-expiry batch and a paid sale row is written. The same logged-in pharmacist holds pharmacy.read/sell/dispense/stock/manage, so there is no hand-off. The toast 'Sale completed — stock decremented' is the only receipt — there is no printout, no change calculation, and no patient linkage (footer is hard-coded 'Linked to: Walk-in').

Large pharmacy

In a large multi-staff pharmacy the counter clerk (holding pharmacy.sell) runs this lane for non-prescription purchases while pharmacists work the prescription dispense queue separately. Volume matters here and several real gaps bite: there is no batch/expiry visibility or choice (the server silently picks FEFO), no on-hand quantity shown in the search dropdown (search results omit on_hand and even the price is rendered raw), no line-level price override, no receipt/invoice, and — most significantly — OTC revenue does NOT flow through the billing Charger/cashier the way prescription dispensing does. The OTC sale is written straight to status 'paid' with a free-text payment_method and no charge_id, so cash reconciliation for OTC happens outside the cashier/finance modules. Separation of duties is weak: the page collects the money itself rather than routing to a cashier.

Small pharmacy

The On hand column with its amber low-stock highlight (d.on_hand <= d.reorder_level) is the practical signal to reorder. Large pharmacy

In a large multi-staff pharmacy, front-line dispensers and cashiers (who typically hold pharmacy.read but not pharmacy.manage) use this as a non-editable lookup of the formulary and live stock, while inventory/managers do the actual catalog and stock changes on the separate admin/batches/purchasing pages. The Class filter lets a user narrow a long formulary (e.g. only "Macrolide"); the Controlled filter isolates controlled substances for spot-checks against the controlled register report. Note the on_hand figure is a SUM across all non-deleted batches regardless of expiry/quarantine status (SQL: SUM(b.qty_on_hand) WHERE deleted_at IS NULL, pharmacy.sql:7) — so a large pharmacy with expired/quarantined lots will see those units still counted in On hand here, which can overstate truly dispensable stock; the per-batch truth lives on the Batches page.

7 · Catalog admin — Drug catalog admin (CatalogAdminPage)

Admin CRUD screen for the pharmacy drug catalog (drugs table): a manager lists every drug with its form/class/reorder level/price and on-hand-derived data, and adds or edits drugs (name, form, class, controlled flag, unit price in ETB, reorder level, active/inactive) via a modal.

Permissions & gating

Frontend: the route is only auth-gated (components/ProtectedRoute.tsx checks login status, no per-route permission check); the nav link in app/nav.ts requires perm "pharmacy.manage". Backend enforces real permissions on the endpoints this page calls: GET /pharmacy/drugs requires "pharmacy.read" (routes.go:15), POST /pharmacy/drugs and PUT /pharmacy/drugs/:id require "pharmacy.manage" (routes.go:31-33). The whole /pharmacy group is also gated by the "pharmacy" feature flag via httpx.RequireFlag("pharmacy") (routes.go:12).

Small pharmacy

In a small single-pharmacist pharmacy, the same person who dispenses also maintains the catalog. They open Catalog admin once to seed their formulary (e.g. "Azithromycin 500mg", Tablet, Macrolide, set unit price in ETB and a reorder level), then return occasionally to bump a price or mark a drug Inactive when they stop stocking it. There is no separation of duties: whoever holds pharmacy.manage does everything. Note: this page only manages the drug master record (pricing, reorder level, controlled flag, active state). It does NOT add stock — actual on-hand quantity comes from batches created elsewhere (stock adjust / PO receive), so a newly created drug shows reorder level and price here but 0 stock until a batch is added on another page.

Large pharmacy

In a large multi-staff pharmacy, catalog maintenance is a manager/lead-pharmacist task gated by pharmacy.manage, separate from front-line dispensers who only hold pharmacy.read/pharmacy.dispense and cannot reach the create/update endpoints (they get a 403). The manager curates a large formulary: setting the controlled flag (is_controlled) so the class-aware allergy guard and controlled-register report pick the drug up, tuning reorder_level per drug to drive low-stock alerts on the dashboard, and standardizing unit_price (ETB) that flows into dispense charges and OTC sales. Inactivating a drug (is_active=false) retires it from the prescriber/dispenser search (SearchDrugs filters on is_active) without deleting history. The table here is unpaged and unfiltered (lists all drugs incl. inactive), which is workable but coarse at large catalog sizes.

Workflow

  1. Page mounts and runs useQuery(['drugs'], listDrugs()) -> GET /pharmacy/drugs with NO query params, so it returns ALL non-deleted drugs (active and inactive) ordered by name.
  2. The catalog renders as a table; each row shows name (with an 'inactive' badge if !is_active), form, class (+ ' (controlled)' suffix if is_controlled), reorder level, and unit price, plus an Edit link.
  3. If there are zero drugs, an empty state 'No drugs yet.' is shown under the table.
  4. To add: click 'Add drug' (top-right). This opens DrugDialog seeded with { isNew:true, is_controlled:false, is_active:true } (Status field is hidden for new drugs).
  5. To edit: click 'Edit' on a row. DrugDialog opens pre-filled from that drug's fields and shows the Status (active/inactive) select.
  6. In the dialog the user fills/edits Name (required), Form, Class, Unit price (ETB), Reorder level, Controlled (No/Yes select), and — on edit only — Status (Active/Inactive).
  7. Save button is disabled until name is non-empty (form.name.trim()). On click it runs the mutation.
  8. Create path: POST /pharmacy/drugs with { name, form?, drug_class?, is_controlled, unit_price (number), reorder_level (number) }. Backend inserts into drugs (is_active defaults true at the DB level; the create request does NOT send is_active).
  9. Update path: PUT /pharmacy/drugs/{id} with the same body PLUS is_active. Backend updates the drugs row.
  10. On success: toast 'Drug added' or 'Drug updated', the dialog closes, and the ['drugs'] query is invalidated so the table refetches.
  11. On error: toast 'Could not save (name may already exist)'. The backend maps a unique-constraint violation on (tenant_id, lower(name)) to a DRUG_EXISTS conflict.

Gaps & observations

DEFAULT PO line cost = drug SELLING price, not purchase cost: PurchasingPage.tsx:149 sets cost: Number(d.unit_price) || 0, where Drug.unit_price is the catalog SELL price. Unless the manager overwrites every line, POs record purchase cost == sell price, which corrupts the 'valuation' and 'margins' reports (service/manage.go ReportStockValuation / ReportMargins). Also SearchDrugs only returns unit_price (pharmacy.sql:15) and the service zeroes reorder_level/is_active/on_hand for search results (service/service.go:74), so those Drug fields are meaningless in the PO picker.
po_items.received is dead/lying data: column exists (migration 00011:48), is selected and surfaced as POItem.Received (ports.go:255, GetPO maps it), but ReceivePO never updates it to true (service/manage.go:197-216). After a PO is received, every line still shows received=false. The PO-level status 'received' is the only real receipt signal.
No partial / split receipt: ReceivePO always creates exactly ONE batch per line at the FULL ordered qty (CreateBatch QtyOnHand: it.Qty, service/manage.go:204) and flips the whole PO to 'received' in one shot. You cannot receive part of a delivery, receive a different quantity than ordered, or split a line across multiple batches/expiries. The UI offers no received-qty field.
Receiving allowed directly from 'draft': the table shows 'Receive' for both 'draft' and 'ordered' (PurchasingPage.tsx:77), and the service does not require 'ordered' first (it only blocks 'cancelled'/'received', service/manage.go:179-185). The 'ordered' state is therefore optional/bypassable — no enforced order->receive sequence.
No edit/cancel of a PO from the UI: although the backend SetPOStatus accepts 'cancelled', PurchasingPage renders NO cancel button (only 'Mark ordered' and 'Receive', PurchasingPage.tsx:74-79). There is no way to cancel, edit lines, or delete a PO once created from this page; a mistaken draft can only be left or received.
No supplier edit/deactivate/delete: SuppliersDialog only lists + adds (PurchasingPage.tsx:96-135). is_active is always true; there is no UI (or endpoint) to edit contact/lead time, deactivate, or remove a supplier. The supplier <select> in New PO shows all suppliers with no active-only filter.
expected_date / lead_time_days are decorative for ordering: expected_date is free-form (not auto-derived from the supplier's lead_time_days), and the page never displays expected_date in the PO table. lead_time_days surfaces only in the 'supplier' report.
No pagination/search/filter on the PO list: ListPOs is a hard LIMIT 100 (purchasing.sql:30) with no UI controls — older POs silently fall off in a busy pharmacy.
Cost has no client-side min: the line 'cost' input (PurchasingPage.tsx:201) accepts negative numbers; only qty is clamped (>=1). Server validates qty>0 but does NOT validate unit_cost>=0 (service/manage.go:121-126), so a negative-cost PO line is accepted end-to-end.
No separation of duties: ordering (CreatePO) and goods-receipt (ReceivePO) are both gated by the single pharmacy.manage permission (routes.go:39,42); a large pharmacy cannot split 'buyer' from 'receiver' roles using the shipped permissions.
Frontend Route is unguarded: router.tsx:77 mounts PurchasingPage with no per-route permission wrapper — gating relies on nav-link visibility + backend 403s, so a user who navigates directly to /pharmacy/purchasing without pharmacy.manage sees the page shell and only fails on the API calls.
po_no uses a global (non-tenant) sequence purchase_orders_po_no_seq (migration 00011:22,26), so PO numbers are not per-tenant-contiguous; tenants see gaps in their PO-#### series.
'Value' column renders the raw total string with no currency symbol/locale formatting (PurchasingPage.tsx:70) despite the ETB market.

9 · Stock control — Stock Control — physical stock-count / cycle-count reconciliation

A count-then-reconcile workflow: a pharmacy stock-keeper starts a count session that snapshots every active drug's system on-hand, enters the physically counted quantity per drug, sees the variance, applies per-line adjustments that write real stock movements, then approves (locks) the count.

route /pharmacy/stock-controlnav: Stock control

Permissions & gating

Module gated by the `pharmacy` feature flag (httpx.RequireFlag("pharmacy"), backend routes.go:12). All six stock-count endpoints require the `pharmacy.stock` permission — they are mounted under the `stock := httpx.RequirePermission("pharmacy.stock")` middleware (routes.go:27, 45-51). Nav entry is shown only to holders of `pharmacy.stock` (frontend/src/app/nav.ts:42, perm: ["pharmacy.stock"]). NOTE: the route in router.tsx:78 has NO per-route client-side permission guard component — the page component renders for anyone who navigates to the URL; access control is enforced server-side, where each API call returns 401/403 without `pharmacy.stock`. No separate approve permission exists — anyone with `pharmacy.stock` can also approve, so there is no separation of duties between counter and approver.

Small pharmacy

In a single-pharmacist shop, the same person who holds pharmacy.stock starts a count (e.g. end-of-month), walks the shelves entering counted numbers per drug, clicks Adjust on each drug where the shelf disagrees with the system (variance badge shows +N green / -N rose), then Approve to lock it. There is NO separation of duties: created_by and approved_by are both just stamped from the acting principal (service.go:697 actorOf -> p.UserID), and nothing prevents the same user creating, counting, adjusting, and approving. Adjust applies the variance to the single largest non-quarantined batch of that drug (service.go:325-356), so for a small shop with one batch per drug this just corrects that batch.

Large pharmacy

A larger pharmacy gets no real multi-user support here. SnapshotStockCountItems snapshots EVERY active, non-deleted drug for the tenant into one count (stock_control.sql:8-15) — a count is always pharmacy-wide; there is no scoping by aisle, location, shelf, or drug class, and no concept of a cycle-count subset. There is no per-line assignment to a counter, no concurrency/locking, and no protection against two counts running at once or against stock moving (dispenses/sales) DURING the count. Variance is frozen at snapshot time as counted - on_hand stored on the line, so on_hand can drift from live stock between snapshot and adjust. The "adjust to largest batch" rule (service.go:313-314 comment calls it a documented simplification) is wrong for FEFO/expiry correctness in a multi-batch pharmacy: a shortage is always pulled from the biggest batch regardless of which batch/lot the shrinkage actually came from, and a surplus with no existing batch creates a synthetic batch literally named "COUNT-ADJ" with NULL expiry (service.go:341). Approve does not require all lines adjusted or all variances zero — it just flips status to approved, leaving unreconciled variances permanently recorded but never posted.

Workflow

  1. 1. User opens /pharmacy/stock-control. The page loads the list of recent counts via listStockCounts() -> GET /pharmacy/stock-counts (max 50, newest first, stock_control.sql:17-19).
  2. 2. User clicks the 'New count' button (top-right, Plus icon). This fires create.mutate() -> createStockCount() -> POST /pharmacy/stock-counts with body {note} (note is always undefined from this page; there is no note input in the UI).
  3. 3. Backend CreateStockCount (service.go:233) inserts a stock_counts row (status defaults to 'open', created_by = actor) then runs SnapshotStockCountItems, inserting one stock_count_items row per active non-deleted drug with on_hand = counted = SUM of that drug's non-deleted drug_batches.qty_on_hand (stock_control.sql:8-15). All in one transaction.
  4. 4. On success the new count id is set as `selected`, switching the page from the list view to the CountDetail view, which calls getStockCount(id) -> GET /pharmacy/stock-counts/:id returning the header + items (each item carries variance = counted - on_hand computed server-side, service.go:285).
  5. 5. For each drug row, user types the physically counted quantity into the 'Counted' number input. On blur, if the value differs from the current counted value, save.mutate() -> setCounted(itemId, counted) -> PUT /pharmacy/stock-count-items/:id/counted with body {counted}. Backend rejects negative values (service.go:301).
  6. 6. After saving, the query is invalidated and re-fetched, so the 'Variance' badge updates (computed as counted - on_hand). +N renders green (emerald), -N renders rose, 0 renders plain outline.
  7. 7. For any line where variance != 0 and not yet adjusted and the count is not locked, an 'Adjust' link appears. Clicking it fires adjust.mutate(itemId) -> adjustCountItem(itemId) -> POST /pharmacy/stock-count-items/:id/adjust (no body).
  8. 8. Backend AdjustCountItem (service.go:315) recomputes variance = counted - on_hand from the stored line, finds the largest non-quarantined batch of the drug (ListBatchesByDrug), applies the variance delta to that batch via AdjustBatchQty (fails INSUFFICIENT_STOCK if it would go negative). If no batch exists and variance>0 it creates a 'COUNT-ADJ' batch; if no batch and variance<0 it errors. It writes a stock_movements row (reason='count', ref_type='count'), then marks the line adjusted=true and sets the line's on_hand = counted.
  9. 9. After adjust + refetch, the line shows the text 'adjusted', the counted input becomes disabled, and the Adjust link disappears. Variance is NOT recomputed to zero in the UI (on_hand stored value was set = counted on the backend, but the GET returns on_hand from the snapshot column which was overwritten to counted, so variance becomes 0 on next fetch).
  10. 10. When done, user clicks 'Approve count' (top-right of detail). approve.mutate() -> approveStockCount(id) -> POST /pharmacy/stock-counts/:id/approve. Backend flips status to 'approved', stamps approved_at=now() and approved_by=actor, but ONLY if status='open' (stock_control.sql:42-44); no error is returned to the user if no row matched.
  11. 11. Once status is 'approved' the detail view is `locked`: the Approve button is replaced by an 'approved' success badge, all Counted inputs are disabled, and no Adjust links render. The list view shows a green 'approved' badge for that count.
  12. 12. User clicks '← All counts' to return to the list.

The UI hides the link after adjust, but a repeated direct POST would apply the (now-zero) variance again — variance recomputed as counted - on_hand and on_hand was set to counted on first adjust, so a second call no-ops on stock but still re-runs (and re-marks adjusted). Not a hard bug but the invariant is enforced only by the client.
'Adjust to largest batch' is a documented simplification (service.go:313-314 comment): shortages are always pulled from the single largest non-quarantined batch regardless of which lot the shrinkage came from; breaks per-batch/FEFO and expiry accuracy in a multi-batch pharmacy.
Surplus with no batch creates a synthetic batch named literally 'COUNT-ADJ' with NULL expiry (service.go:341) — an unlabeled, never-expiring lot that pollutes batch/expiry reports.
Snapshot is whole-tenant only: SnapshotStockCountItems counts every active drug (stock_control.sql:8-15). No cycle-count / partial / by-location / by-class scoping despite the page being described as cycle-count. No location concept exists in the schema.
Race / staleness: on_hand is frozen at snapshot. Dispenses, OTC sales, receiving, and manual adjustments that occur between snapshot and Adjust are NOT reflected — the adjust posts a delta based on the stale stored on_hand, so it can over/under-correct live stock. No locking, no recompute-at-adjust against live batch totals.
No separation of duties / no approval gate on reconciliation completeness: ApproveStockCount only flips status if 'open' and does not require all lines adjusted or all variances zero (stock_control.sql:42-44). The same user (pharmacy.stock) can create, count, adjust, and approve. created_by vs approved_by are recorded but never compared.
Silent no-op approve: POST .../approve returns 204 even when no row matched (e.g. already approved) — the UI would show a success toast 'Count approved' regardless (StockControlPage.tsx:76).
stock_movements.ref_id is left NULL for count adjustments (service.go:353 only sets ref_type='count'), so a movement cannot be traced back to the originating count or count-item via ref_id — weak audit linkage.
No delete / cancel / abandon of a count: there is no endpoint or UI to remove or void an 'open' count; a started count lives forever in the list (only the most recent 50 are shown).
'note' is dead in this UI: CreateStockCount accepts a note (service.go:233, column stock_counts.note) but StockControlPage.tsx:18 always calls createStockCount() with no argument, and ListStockCounts/GetStockCount handlers never return note. So the note field is effectively unused from the product.
No empty-snapshot handling: if the tenant has zero active drugs, a count is created with zero items; the detail table just shows an empty body with no dedicated empty state (only the list view has the 'No counts yet' empty state).
No pagination on the list: ListStockCounts is hard-capped at LIMIT 50 (stock_control.sql:19) with no paging UI; older counts become inaccessible from this page.

Small pharmacy

In a single-pharmacist shop the same person who dispenses also holds pharmacy.manage. They open Reports occasionally: "Stock valuation" to see cash tied up in stock, "Wastage/expiry" before a clear-out, and "Controlled drugs" when a regulator/inspector asks for the controlled-substance register (it dumps the most recent 100 controlled stock movements with timestamp, drug, +/- change, and reason). They mostly hit Export to get a CSV to open in Excel; on-screen View is a quick sanity check. Because the page has NO date filters and NO parameters, the small operator just exports the whole dataset and filters/sums in the spreadsheet.

Large pharmacy

In a multi-staff pharmacy this is the manager/owner's tool, walled off by pharmacy.manage from the dispensing clerks (pharmacy.dispense), OTC cashiers (pharmacy.sell) and stock counters (pharmacy.stock). The manager reviews "Consumption" (top-20 dispensed/sold drugs) for demand planning, "Margins" (sell price vs average PO unit cost) for pricing, and "Supplier performance" (PO counts, received counts, lead-time-days) for vendor reviews. "Controlled drugs" provides the compliance register. Volume limits matter: Consumption is hard-capped at top 20 drugs and Controlled at the latest 100 movements, so a high-throughput pharmacy will NOT get a complete picture from these two reports — they are summaries, not full audit exports. There is no scheduling, no email delivery, no role beyond pharmacy.manage, and no period selection, so the manager runs everything ad hoc against the entire tenant history.

Server-side CSV export is NOT implemented and is explicitly deferred: reports.sql:1 and reports.sql.go:30 comment say 'CSV export deferred'. Export is done entirely client-side (ReportsPage.tsx:20-33,39-53) by re-fetching the JSON and serializing in the browser. The page header even contrasts with other pharmacy pages that gained a 'unified date-range filter' (commit c23f8bc); Reports was not included.
Hard limits cap the data: Consumption is LIMIT 20 (reports.sql:9) and Controlled register is LIMIT 100 (reports.sql:25). A busy pharmacy's controlled-substance register is therefore truncated to the most recent 100 movements — NOT a complete regulatory export despite the 'Register & audit' framing (ReportsPage.tsx:15).
Margins shows Sell and Avg cost but does NOT compute the margin itself (no margin amount or %, no negative-margin flag). The user must compute it in the spreadsheet. Drugs never purchased via a PO get avg_cost = 0 (COALESCE), making the margin look like 100%.
Valuation values stock at SELL price (qty_on_hand * d.unit_price), labeled 'Value on hand' (reports.sql:15). This is retail value, not cost-basis inventory value — it overstates the accounting value of stock. There is no cost-based valuation report.

Wastage groups expired AND quarantined batches into one 'value at risk' list with no separation between the two reasons and no expiry-window (near-expiry) bucket — only already-expired (expiry_date < today) or quarantined are shown; soon-to-expire stock is not reported here.
The frontend Report interface is generic {columns:string[], rows:string[][]} (api.ts:171-174) with all values pre-stringified server-side; the client cannot sort, type, or right-align numeric columns — currency/quantities render as plain left-aligned text.

Data model

Stock representation

Stock-on-hand is STORED batch-by-batch in drug_batches.qty_on_hand (INTEGER). It is NOT computed from the stock_movements ledger - stock_movements is an append-only AUDIT trail only and is never summed to derive on-hand. A drug's total on-hand is computed on read as COALESCE(SUM(b.qty_on_hand) WHERE drug_id=d.id AND deleted_at IS NULL,0) (see ListDrugs, DispenseQueueKpis, SnapshotStockCountItems, reports). FEFO dispensing: ListBatchesByDrug orders by (expiry_date IS NULL), expiry_date, batch_no (earliest expiry first, nulls last); availability/quarantine/expiry checks happen on dispense in service code, not in SQL/DB. Decrements use guarded UPDATEs: DecrementBatch sets qty_on_hand=qty_on_hand-@qty WHERE qty_on_hand>=@qty RETURNING (no row => insufficient stock, caller errors); AdjustBatchQty sets qty_on_hand=qty_on_hand+@delta WHERE qty_on_hand+@delta>=0 RETURNING (no row => would go negative, treated as conflict). Receiving a PO creates new batches (CreateBatch) + records a stock_movement; it does not mutate existing batch qty.

Money representation

All money is NUMERIC(12,2) at the DB level, surfaced as Go `string` in models.go (sqlc maps numeric->string to avoid float). Currency is ETB: pharmacy_sales.currency TEXT NOT NULL DEFAULT 'ETB'. drugs.unit_price = sell price; po_items.unit_cost = buy cost (distinct). pharmacy_sales carries subtotal, total, discount (00010), tax (00010); pharmacy_sale_items carries unit_price + line_total (stored, not generated). po_items.line_total and purchase_orders.total are stored. No minor units/cents - decimal ETB throughout.

RLS posture

Every pharmacy table has RLS ENABLED and FORCED with a single policy named tenant_isolation USING/WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid). Applied in 00008 to drugs, drug_batches, stock_movements, pharmacy_sales, pharmacy_sale_items; in 00011 to suppliers, purchase_orders, po_items, stock_counts, stock_count_items; in 00022 to allergen_catalog, drug_catalog, drug_allergens. Each migration also conditionally GRANTs SELECT/INSERT/UPDATE/DELETE on its tables to role clinic_app (IF that role exists) and GRANTs USAGE,SELECT on the relevant sequences (prescriptions_rx_no_seq in 00008, purchase_orders_po_no_seq in 00011). FORCE RLS means even the table owner is subject to the policy; per project memory the app must connect as the non-superuser clinic_app role and set app.tenant_id per request for isolation to bind.

Integrity guards (00009)

  • SURPRISING: migration 00009 (named '..._integrity_guards') contains NO triggers and NO CHECK constraints. It adds only (1) UNIQUE INDEX idx_prescriptions_rx_no ON prescriptions(rx_no) to guarantee Rx numbers are globally unique, and (2) INDEX idx_prescriptions_dispense(tenant_id, dispensed_at) WHERE deleted_at IS NULL to speed dispense-queue/dispensed-today reads. Its comment states per-tenant contiguous Rx numbering is deferred and uniqueness is the only correctness requirement here.
  • There are NO DB-level CHECK constraints guaranteeing qty_on_hand>=0, qty>0, or delta sign. Stock non-negativity is enforced purely by guarded UPDATE WHERE-clauses (DecrementBatch: qty_on_hand>=@qty; AdjustBatchQty: qty_on_hand+@delta>=0) that return no row on violation - the app layer must detect the missing row.
  • Double-dispense guard is an atomic optimistic claim, not a constraint: MarkPrescriptionDispensed UPDATEs dispensed_at=now() WHERE dispensed_at IS NULL RETURNING id (row returned only on first claim).
  • Double-receive guard is also an atomic claim: SetPOReceived UPDATEs status='received' WHERE status NOT IN ('received','cancelled') RETURNING id, preventing concurrent double stock-in.
  • Status integrity is enforced via CHECK constraints (not triggers): pharmacy_sales.sale_type CHECK IN ('dispense','otc'); pharmacy_sales.status (expanded in 00017 to awaiting_payment/charged/paid/cancelled/dispensed); purchase_orders.status CHECK IN ('draft','ordered','received','cancelled'); stock_counts.status CHECK IN ('open','approved').
  • stock_movements.reason has NO CHECK despite the comment enumerating dispense/otc_sale/adjust/receive/return - any free-text value is accepted.
  • Stock-count approval is gated by status: ApproveStockCount runs only WHERE status='open'.

Notable / surprising

  • TWO separate drug tables that are NOT linked: `drugs` (00008, dispensing/inventory master, has unit_price/batches/stock) vs `drug_catalog` (00022, prescribing library, has default dose/freq/duration). prescription_items.drug_id FKs to drug_catalog, while pharmacy_sale_items.drug_id and all stock tables FK to drugs. Nothing joins a prescribed catalog drug to a dispensable inventory drug - dispense matching is by free-text prescription_items.drug_name.
  • charge_id on pharmacy_sales (added in billing migration 00017, not a pharmacy migration) is UUID with NO foreign key to charges - the billing link is unenforced at the DB.
  • Both human-friendly numbers use GLOBAL sequences, not per-tenant: prescriptions.rx_no (globally unique via idx_prescriptions_rx_no) and purchase_orders.po_no (no unique index at all). So Rx numbers are not per-tenant contiguous and PO numbers are neither per-tenant nor guaranteed unique.
  • stock_movements is a write-only audit log never read to compute balances; on-hand authority is drug_batches.qty_on_hand. Ledger and balance can diverge - nothing reconciles them.
  • drug_allergens composite PK is (drug_id, allergen_id) and deliberately excludes tenant_id (safe only because both FK parents are tenant-scoped). No surrogate id, no timestamps.
  • Denormalization: pharmacy_sale_items.description and prescription_items.drug_name duplicate the drug name as free text; line_total/total are stored (not generated columns) so they can drift from qty*unit_price.
  • quarantined/expired/is_active filtering is enforced in service/handler code, not in SQL or DB constraints - query comments say 'Availability (stock / quarantine / expiry) is enforced on dispense'. ListBatchesByDrug returns quarantined and expired batches.
  • Soft-delete is inconsistent: stock_movements, pharmacy_sale_items, po_items, stock_counts, stock_count_items, drug_allergens have NO deleted_at; stock_counts also lacks updated_at.
  • OTC sales are created already 'paid' with paid_at=now() (CreateOtcSale), bypassing the awaiting_payment two-phase flow used for prescription dispenses.
  • All PKs use gen_random_uuid() (UUIDv4) despite project memory citing a UUIDv7+prefixed-ID decision - the pharmacy schema does not implement prefixed/v7 IDs.

End-to-end workflows

Prescription dispensing (two-phase pre-pay: Rx -> price/send-to-cashier -> hand-over)

Actors: Doctor signs the Rx upstream in the encounter/prescription module (permission prescription.create, not part of pharmacy routes). Pharmacist/pharmacy_manager (pharmacy.read to view queue/detail; pharmacy.dispense to prepare and complete). Cashier collects payment in the billing module (payment.collect). The pharmacist who runs CompleteDispense is recorded as the stock-movement actor (created_by from the request principal).

  1. UPSTREAM (not in pharmacy code): a doctor signs a prescription; the prescription gets rx_no (sequence prescriptions_rx_no_seq) and dispensed_at stays NULL. The Rx only enters the pharmacy queue once its encounter is e.status = 'closed' (ListDispenseQueue / DispenseQueueKpis both JOIN encounters and filter e.status = 'closed' AND p.status <> 'cancelled' AND p.deleted_at IS NULL).
  2. 1. Pharmacist opens GET /pharmacy/dispense-queue (DispenseQueuePage). Each row shows item_count, a has_allergy-derived flag rendered as 'allergy check', and a status badge derived from booleans: dispensed (p.dispensed_at set), awaiting_payment (a pharmacy_sales row with status='awaiting_payment' exists), else 'ready'. KPIs: to_dispense, dispensed_today, low_stock, near_expiry.
  3. 2. Clicking a non-dispensed row navigates to /pharmacy/dispense/:id -> GET /pharmacy/dispense/:id (DispenseDetail). The service loads the header, the patient's allergy substances (ListPatientAllergiesForDispense), and each prescription_item. Each item's free-text drug_name is matched to a catalog drug by case-insensitive exact name (FindDrugByName, lower(name)=lower(@name)); if matched it attaches MatchedDrugID, runs allergyMatchesDrug (token >=4 chars, matches drug name OR drug_class), and lists that drug's batches in FEFO order (ListBatchesByDrug: ORDER BY (expiry_date IS NULL), expiry_date, batch_no). It also surfaces Prepared / PreparedTotal / ChargeSettled if an awaiting_payment sale already exists.
  4. 3. PREPARE (phase 1): pharmacist picks batch + qty per line and clicks 'Send to cashier' -> POST /pharmacy/dispense/:id/prepare with lines [{drug_id,batch_id,qty}] + counselling_notes. PrepareDispense: rejects if already dispensed (ALREADY_DISPENSED) or already prepared (ALREADY_PREPARED); re-checks allergy per line (hard block ALLERGY_CONFLICT); validates each batch via checkBatch (batch belongs to drug, not quarantined, not expired); prices each line at drug.unit_price (parseMoney), sums subtotal. NO STOCK IS MOVED in this phase.
  5. 4. PREPARE bills: calls billing.RaiseChargeTx with Source:'pharmacy', Description 'Pharmacy: Rx #<rx_no> (<n> items)', Amount=total. This creates a billing 'charge' row in status 'pending' (no ToTriage routing). Then CreateSale inserts pharmacy_sales (sale_type='dispense', status='awaiting_payment', charge_id set, Currency 'ETB') and CreateSaleItem rows capturing the chosen drug_id/batch_id/qty/unit_price/line_total. Publishes event 'pharmacy.dispense.prepared'. Returns {sale_id, charge_id, total}.
  6. 5. CASHIER collects (in the billing module, NOT a pharmacy endpoint): the pending pharmacy charge appears in the patient's charge list; a cashier with payment.collect settles it, flipping the billing charge to 'paid' (or 'waived' via payment.waive).
  7. 6. COMPLETE (phase 2): pharmacist clicks 'Complete dispense' (enabled only when charge_settled) -> POST /pharmacy/dispense/:id/complete. CompleteDispense re-fetches the awaiting sale; if none -> NOT_PREPARED. Pre-pay gate: ChargeStatusTx must return 'paid' or 'waived', else PAYMENT_PENDING. It then atomically claims the prescription (MarkPrescriptionDispensed sets dispensed_at only if currently NULL; no row -> ALREADY_DISPENSED, the double-dispense guard).
  8. 7. COMPLETE moves stock: for each prepared sale item it re-checks allergy and re-runs checkBatch, then DecrementBatch (UPDATE ... qty_on_hand - qty WHERE qty_on_hand >= qty; no row -> INSUFFICIENT_STOCK) and InsertStockMovement (delta = -qty, reason='dispense', ref_type='prescription', ref_id=rxID). Finally MarkSaleDispensed (status -> 'dispensed', paid_at=now()). Publishes 'pharmacy.dispensed'. UI navigates back to /pharmacy/queue.
  9. EDGE: if an item's drug_name does not match the catalog, or no available batch (qty>0, not quarantined, not expired) exists, the UI shows 'Not in stock — print & buy outside' and that line is simply omitted from the dispensable lines (no partial-fill tracking; the prescription is still marked fully dispensed on Complete).

Status transitions

prescriptions.dispensed_at: NULL -> now() (claimed atomically at Complete). pharmacy_sales.status: 'awaiting_payment' (created at Prepare) -> 'dispensed' (at Complete, paid_at set). billing charge: 'pending' -> 'paid' (cashier) or 'waived'; the CHECK constraint pharmacy_sales_status_check allows ('awaiting_payment','charged','paid','cancelled','dispensed') after migration 00017. Queue badge derives 'ready' | 'awaiting payment' | 'dispensed' from dispensed_at + awaiting_payment boolean. There is also a CancelAwaitingSale query (status 'awaiting_payment' -> 'cancelled') defined in SQL but NOT wired to any service method or route.

Billing integration

Pre-pay model. PrepareDispense calls billing.Charger.RaiseChargeTx inside the same pgx.Tx, creating a 'pending' charge with Source='pharmacy' (so revenue reaches the cashier in billing). The charge is NOT routed to triage. CompleteDispense gates hand-over on billing.Charger.ChargeStatusTx returning 'paid' or 'waived'. Stock decrement and sale finalisation only happen after the cashier collects.

Small vs big pharmacy

There are exactly two seeded pharmacy roles in provision.go RoleGrants: 'pharmacist' (pharmacy.read+dispense+stock+sell) and 'pharmacy_manager' (all of those plus pharmacy.manage). SMALL PHARMACY (one or two staff): a single 'pharmacy_manager' realistically holds everything and operates all pages personally — sets up the catalog (CatalogAdminPage), purchases and receives stock (PurchasingPage), runs the dispense queue and OTC counter, and does/approves counts (StockControlPage). So in practice the small shop's separation of duties is just pharmacist-vs-cashier, and even that can collapse if one person holds both the pharmacy_manager role and a cashier role (payment.collect). LARGE PHARMACY (multi-staff, separation of duties): the intended split is pharmacy_manager owns catalog + suppliers/POs + goods receipt + reports (pharmacy.manage), while line pharmacists/techs run dispensing, OTC, quarantine, adjustments and cycle counts (pharmacy.read/dispense/sell/stock). Procurement goods receipt is ALL-OR-NOTHING per PO: ReceivePO creates one batch per po_item with the line's full qty and never sets po_items.received=true (the column is exposed in the API/DTO but never written). No partial receipt, no quantity-received-vs-ordered reconciliation, no back-orders.
No accounts-payable / supplier-payment integration: POs carry cost totals but no payable is raised and no money flows through billing for procurement.
OTC sale performs NO allergy check (allergyMatchesDrug is only called in PrepareDispense/CompleteDispense, never in SellOTC) and OTC does not go through the billing Charger — it self-records status='paid' with an in-row payment_method, so OTC cash bypasses the cashier/charges spine entirely.
Stock-count approval does NOT enforce or auto-apply adjustments: a count can be Approved while variance lines remain un-adjusted; only the per-line Adjust action moves stock. Approval and Adjust are both gated by the same pharmacy.stock permission, so there is no segregation between counter and approver.
AdjustCountItem applies the entire drug-level variance to the single LARGEST non-quarantined batch (explicitly a 'documented simplification' in the code), or invents a 'COUNT-ADJ' batch — so batch-level accuracy/FEFO integrity after a count is approximate.
CancelAwaitingSale SQL query exists (status awaiting_payment -> cancelled, e.g. patient declines at cashier) but is NOT wired to any service method or HTTP route, so there is no implemented way to cancel/void a prepared-but-unpaid dispense from the pharmacy side; such a prescription would stay stuck 'awaiting payment' (and PrepareDispense would block re-prep with ALREADY_PREPARED).
Quarantine and batch adjustment have no maker/checker workflow and no reason taxonomy beyond a free-text reason/note; expired stock is only surfaced via the dashboard 'expired -> return' alert and the 'wastage' report — there is no write-off/destruction workflow.
Reports are read-only tabular dumps with no date-range parameters; the 'valuation' report values stock at sell-price unit_price (ValueOnHand / ReportStockValuation use d.unit_price), not at cost, so it is a retail valuation, not a cost/inventory valuation.
