Tooth chart: easier to mark, select and clear

A plan to change how the dentist marks the tooth chart so it takes a few taps instead of dozens, supports marking many teeth at once, and can clear one tooth, a group, or the whole chart safely. Written from the current code and your description. Nothing is built yet: this is for your review, feedback and approval.

In one paragraph. Today you tap a tooth and it cycles through the conditions one at a time, so reaching "Crown" takes five taps and going one too far means going all the way round again. There is no way to mark many teeth together and no clear button. The redesign puts the conditions in a bar above the chart. You pick a condition once, then tap or drag across teeth and they take it. Or you select teeth first (all, upper, lower, one side, only the unmarked, every decayed one) and apply a condition to the whole group in one move. Clear removes marks from one tooth, a selection, or the whole chart, and every change can be undone. Saving stays automatic. The server needs no change.

2. The idea: two simple ways in, one bar for both

A. Condition first, then teeth (for marking). Tap Decayed in the bar. It lights up as the active condition ("Marking: Decayed"). Now every tooth you tap, or drag a finger or mouse across, becomes Decayed. Tap Filled and carry on. One tap per tooth, no cycling, no going round. Tap the condition again, or press Esc, to stop.
B. Teeth first, then condition (for groups). Press Select. Tap teeth to select them, or use the quick buttons: All, Upper, Lower, each quadrant, Unmarked only, Same as this tooth, Invert. Then tap a condition in the bar (or Clear) and every selected tooth changes at once, as one save and one Undo.
Tapping a tooth with nothing chosen opens a small menu right at the tooth with the conditions and Clear. Two taps, no cycling, no mode to learn. That is how a casual single change works.

Small things that make it clearer

  • Right and left are labelled and a centre line is drawn, so it reads like the paper chart.
  • Each condition has a letter or symbol on the tooth (D, F, ✕, C, B), so it still reads in black and white and for colour-blind staff.
  • "Not marked" and "Healthy" stay different. Not marked means nobody has looked; Healthy means somebody did. A quick button marks all the unmarked teeth Healthy after a normal check-up.
  • The legend becomes the bar, so it is no longer a decoration that looks clickable.
  • A one-line summary under the chart: how many are marked and how many of each condition.
  • "Saved" in the bar instead of a pop-up for every tooth. One pop-up only when a group is applied, with Undo.
  • Condition names start with a capital ("Bridge", not "bridge"), whatever the clinic typed.

6. Safety: nothing is lost by accident

  • Selecting is never saved. It only highlights. Only applying a condition changes the record.
  • Clearing a group or the chart always says how many marks before it happens. The whole chart needs a confirmation; one tooth does not.
  • Every change, including a group, is one Undo that stays in the bar, not only for a few seconds.
  • Same protections as today: a failed save puts the chart back to what the server confirmed; two people editing different teeth both keep their work; the chart is read-only while the clinic's conditions are loading or failed to load; people without edit rights see the chart without the bar.
  • The history stays. Every save already writes each tooth's old and new condition to the audit trail; a group change writes one entry per tooth.

7. How it is built

Frontend

  • No new libraries. The existing popover, dialog and toast, plus Tailwind.
  • New pieces: a condition bar, a selection layer on the chart, a tooth menu, and a small history of actions for Undo and Redo. The chart component is rewritten. The save logic in the dental workspace (the draft, the confirmed copy, the queue, the delay, the revert on failure) is kept and extended from "one tooth" to "many teeth in one change".
  • Tap-to-cycle is removed. Nothing else depends on it.
  • The tooth picker used by visits already has quadrant and "all decayed" shortcuts. It keeps working and will share the same quick-select code, so the two behave alike.
  • Phone: follows the shipped mobile conventions (bottom bar above the tab bar, 16 px text, teeth at least 40 px, bottom-sheet dialogs). Horizontal drag is captured only inside the chart.

Backend

None needed. The save endpoint already takes any set of teeth in one request (an empty value clears a tooth), checks every tooth and condition, applies it under a lock and records the history. "Clear all" is up to 32 teeth in one request. I will add server tests that prove a whole-chart apply and a whole-chart clear work in one request, and that one bad tooth refuses the whole request.

8. Functional testing plan

LayerWhat is proved
Server tests
  • 32 teeth set in one request; 32 cleared in one request; the result equals what was sent.
  • One invalid tooth or unknown condition refuses the whole request and changes nothing.
  • Two clinicians changing different teeth at the same moment both keep their changes; for the same tooth the later wins and both are in the history.
  • A user without edit rights is refused; another clinic's patient is not reachable.
Screen tests
  • Pick a condition, then tap teeth: each tooth gets it, as one save.
  • Drag across a row: every tooth under the pointer is marked once.
  • Select mode: each quick select picks exactly the right teeth; applying changes only those; the selection is not saved.
  • Clear a tooth, clear a selection, clear the whole chart (asks first, shows the count, Cancel does nothing).
  • Undo and redo for single and group changes; a failed save reverts the chart.
  • Tapping with nothing chosen opens the menu; the menu applies and closes.
  • Read-only users: no bar, no menu, teeth cannot be changed. Conditions loading or failed: read-only with Retry.
  • Keyboard use, letters on teeth, labels present; phone layout at 320, 375 and 414 px with no sideways scroll.
  • The existing nine chart tests are migrated to the new behaviour, none dropped without a replacement.

10. Risks, and how each is handled

  • A slip changes many teeth at once. Group actions show the count, clearing the whole chart asks first, and every group change is one Undo that stays in the bar.
  • Dragging on a phone can fight with scrolling the page. Drag is active only inside the chart while a condition is chosen, vertical scrolling still works, and Select mode is the fallback.
  • Dentists used to tap-to-cycle. Tapping a tooth with nothing chosen still does something obvious (a small menu), so nobody is stuck, and the bar explains itself ("Pick a condition, then tap teeth").
  • The chart is a clinical record. The save path that protects it is kept, and the new group paths go through the same code with their own tests.

11. Decisions for you

My recommendation is first in each line.

  1. Remove tap-to-cycle completely? Recommend: yes. Tapping a tooth with nothing chosen opens the small menu instead.
  2. Tapping a tooth that already has the active condition: Recommend: leave it as it is (use Clear to remove). The alternative clears the mark, which is quicker but easier to do by accident.
  3. Who can clear the whole chart? Recommend: anyone who can edit the chart, with the confirmation and Undo. The alternative is dentists and managers only.
  4. Keep "Healthy" separate from "not marked"? Recommend: yes, with a one-tap "mark the unmarked Healthy".
  5. Letters on teeth (D, F, ✕, C, B)? Recommend: yes. Clinics still choose their own colours.
  6. Children's (milk) teeth now or later? Recommend: later, in phase 4. It needs new tooth codes and server checks.
  7. Chart history view now or later? Recommend: later. The data is already being recorded.
  8. Start with phase 1, check it, then phases 2 and 3? Recommend: yes.
