VPS infrastructure audit

77.68.116.240 — hosting The Millions and ClinicOS · 24 September 2026

The expired certificate was not the problem. It was the symptom. The site was unreachable for seven days and the way it was discovered was the owner looking at it. Nothing on this machine watches anything, nothing backs anything up, and nothing renews anything. The certificate is fixed until 23 December; the reason it expired is not.

01What actually happened

Diagnosed in order, discarding two plausible causes that were not it.

DNSAll three hostnames resolve to 77.68.116.240. Correct.
Ports 80/443Open from the public internet. Correct.
nginxServing 200 on the box the entire time. Working.
TLS certificateExpired 17 September. Browsers refused to connect.
subject = CN = the-millions.co.uk
issuer  = Let's Encrypt
notAfter= Sep 17 10:16:09 2026 GMT     ← seven days before this audit

Two things looked guilty and were not:

  • The nginx container reports unhealthy — but it has failed its healthcheck 259,656 times at the moment of diagnosis — months of continuous failure while serving the site perfectly. The healthcheck is broken, not nginx.
  • The ACME challenge path returns 404, because the compose file mounts a Docker named volume at /var/www/certbot while issue-cert.sh writes to a host directory of the same name. Harmless today only because the script uses certbot --standalone.

Fixed

Ran deploy/issue-cert.sh. New certificate valid 24 Sep → 23 Dec 2026, covering the-millions.co.uk, www and staging. Site returns 200 with full certificate validation. ClinicOS untouched.

02The issues, and whether the fix is permanent

Ordered by what will cause the next outage, not by how interesting it is.

Critical  1 — The disk is 81% full and every deploy makes it worse

86 GB of the 116 GB disk is Docker build cache inside /var/lib/containerd. It grows with every ClinicOS deployment and nothing ever clears it.

/dev/vda1   116G   93G   23G   81%  /
/var/lib/containerd              86G
docker build cache         90.59GB   (30.1GB reclaimable immediately)

Why this is the top item: PostgreSQL for both businesses lives on this disk. When it fills, writes fail — that is not a slow degradation, it is both companies down at once, with a real risk of database corruption rather than a clean stop.

Solution

Immediate: docker builder prune -af reclaims roughly 30 GB in under a minute, safely — build cache is regenerated on the next build and holds nothing unique.
Permanent: a weekly scheduled prune, plus a disk-usage alert at 80%.

Permanent after fix? Only with the schedule. A one-off prune buys months and then the same wall.

Critical  2 — Neither database has ever been backed up

No dump exists anywhere on this machine. deploy/pg-backup.sh and restore-backup.sh were written and nothing has ever called them.

find /home/themillions -name "*.sql*" -o -name "*.dump"   →   (nothing)
cron jobs: 0        systemd backup timers: 0

What is at stake: 677 patient records across eight clinics, including Cure Dental's 604 — a real dental practice whose clinical history exists in exactly one place, on one disk, on one machine, with no copy. Plus The Millions' own database.

Solution

Nightly pg_dump of both databases, written offsite. Cloudflare R2 is already configured and paid for on this box, so this costs nothing new. Then — and this is the part people skip — a restore rehearsal, because a backup nobody has restored is a hypothesis.

Permanent after fix? Yes, once scheduled and verified.

Critical  3 — Nothing watches either site

The site was down for seven days. The detection mechanism was a human noticing. There is no uptime check, no certificate-expiry warning, no alert of any kind.

This is the issue that produced the other ones. A machine nobody is watching accumulates silent failures — and this audit found three more that are currently invisible in exactly the same way.

Solution

An external uptime monitor on both domains — one that checks from outside the box, because a check running on the server cannot tell you the server is unreachable. It must alert on certificate expiry ≥ 14 days ahead, which alone would have prevented this outage.

Permanent after fix? Yes. This is the single highest-value hour on the list.

High  4 — Certificate renewal is still manual

No cron job, no systemd timer, no certbot container. The June certificate was issued by hand and nothing was ever going to renew it. Today's fix has the same property.

Solution

0 4 * * 1  cd /home/themillions/The-Millions/deploy && ./issue-cert.sh >> /var/log/cert-renew.log 2>&1
The script already no-ops when more than 30 days remain, so weekly is safe. Note it stops nginx for a few seconds to free port 80 — acceptable at 4am Monday, and removable by fixing the webroot mount (item 8).

Permanent after fix? No — not yet. Today it expires again on 23 December 2026 unless the schedule is added.

High  5 — 130 days uptime, 7 security updates pending, reboot required 
uptime:                  130 days
pending security updates: 7
/var/run/reboot-required: YES

Unattended-upgrades is running, so packages are patched — but a kernel update only takes effect after a reboot, and this machine has not rebooted in over four months.

Solution

Reboot during a quiet window. Every container is set to always or unless-stopped, so the stack comes back on its own — I verified the restart policies rather than assuming them.

Permanent after fix? Recurring by nature — needs a quarterly habit, not a one-off.

Medium  6 — Container logs grow without limit

224 MB today and no max-size configured on any container. Slow, but it only ever goes one way, and it shares the disk with item 1.

Solution

Set max-size: 10m / max-file: 3 in the Docker daemon config — one file, applies to everything, survives redeploys.

Permanent after fix? Yes.

Medium  7 — The nginx healthcheck has never worked

wget: can't connect to remote host, continuously. The counter stood at 259,656 consecutive failures when this audit began; restarting nginx to install the new certificate reset it, and it was back to 28 and climbing within the hour — so the check is still broken, it has simply lost its evidence.

The cost is not cosmetic: a genuinely broken nginx would look identical to today. The one signal that could have told you something was wrong has been crying wolf since June.

Solution

Point the healthcheck at a port nginx actually listens on, or remove it. A check that is always red is worse than no check.

Permanent after fix? Yes.

Low  8 — Webroot mount mismatch forces downtime to renew

docker-compose.prod.yml mounts the named volume certbot-webroot at /var/www/certbot; issue-cert.sh writes to the host directory deploy/certbot-webroot. Different places, so HTTP-01 webroot validation can never succeed and renewal must stop nginx instead.

Solution

Change the mount to a bind on the same host directory, then renew with --webroot and no downtime at all.

Permanent after fix? Yes.

Low  9 — Duplicate nginx server block 
[warn] conflicting server name "the-millions.co.uk" on 0.0.0.0:443, ignored

Emitted on every start. Harmless now — one block silently wins — but it means the config does not say what its author thinks it says, which is how a future edit lands in the block that is ignored.

Permanent after fix? Yes.

Low  10 — Historical secrets left on disk

Eleven .env snapshots sit in clinicos/.history/, written by an editor extension, each containing the database password and API keys as they were on that date. Rotated credentials are still readable there.

Solution

Delete the directory and add .history/ to .gitignore so it never reaches the repository.

Permanent after fix? Yes.
